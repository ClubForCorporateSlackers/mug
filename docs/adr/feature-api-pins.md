## 判断：geohash を5文字から4文字に変える（読み込みユニットに収めるため）

- 状態：承認

### 状況（何に迷ったか）

docs/db-schema.md では、Pins の `cell` は geohash 5文字（約5km四方）。`GET /api/pins` は表示範囲にかかる `cell` ごとに Query する。0.5度四方まで許すので、Query の回数と読み込みユニット（Pins は 10）に収まるかを確かめるよう指示された。

### 計算

DynamoDB の Query は、読んだデータの合計を4KB単位で切り上げて数える。結果整合性の読み込み（今回の設定）は 4KB ごとに 0.5 ユニット。**中身が0件でも1回 0.5 ユニット**かかる。

| 文字数 | マスの大きさ（度） | 日本付近（北緯35度） | 0.5度四方にかかるマスの数（最大） | 0件でも使うユニット |
|---|---|---|---|---|
| 5 | 経度0.044 × 緯度0.044 | 約4km × 4.9km | 13 × 13 ＝ **169回** | 約85 |
| **4** | 経度0.35 × 緯度0.18 | 約32km × 20km | 3 × 4 ＝ **12回** | **6** |
| 3 | 経度1.41 × 緯度1.41 | 約128km × 156km | 2 × 2 ＝ 4回 | 2 |

- 5文字：地図を一番広く開くだけで約85ユニット。Pins の10ユニットの8倍以上で、1回で溜めておける分（バースト、最大で約300秒分）を使い切りながら読むことになり、何人かが同時に地図を動かすとエラー（スロットリング）になる。169回の Query を Lambda から同時に出すので、待ち時間も長い
- 4文字：0件なら6ユニット。ピン1件は約0.3KBなので、1マスに200件たまっても約60KB（約8ユニット）。ハッカソンの件数（数十〜数百件）なら、ほぼ1回あたり 6〜10 ユニット
- `test/geo.test.ts` で、0.5度四方のマスの数が4文字で最大12、5文字で150以上になることを確かめている

### 決めたこと

- geohash を **4文字**にした（`infra/lambda/api/geo.ts` の `GEOHASH_PRECISION`。1か所を変えれば戻せる）
- docs/db-schema.md の Pins の説明と未決定の欄を書き換えた
- まだ本番の Pins にデータがないので、今なら変えても移し替えが要らない

### 理由

- 5文字では、地図を開くたびにユニットが足りなくなる
- 3文字はマスが大きすぎて、拡大した地図でも周り100km以上のピンを読んでから捨てることになる

### ほかの案

- 5文字のまま、許す範囲を0.1度にする：地図をあまり広く見られなくなり、api-spec.md の0.5度と合わない
- geohash をやめて、0.25度ごとの自前のマス目にする：4文字とほぼ同じ効果だが、db-schema.md からの変更が大きい
- Pins の読み込みユニットを増やす：合計25以内（無料枠）の約束で、ほかのテーブルから回せる余裕がない

### 影響・あとで見直すこと

- 1マス（約32km×20km）に200件より多くたまると、拡大した地図でも、そのマスの古いピンは出てこない（`truncated: true` になり「拡大してください」と出るが、拡大しても同じマス）。ハッカソンの件数では起きない見込み。件数が増えたら、マスごとに続きを読む（ページ送り）か、5文字に戻して範囲を狭くする
- 1件の Query で読むのは最大200件（Limit）。全部のマスがいっぱいだと 1回の地図表示で約100ユニットになりうる

## 判断：GET /api/pins の truncated は「読み切れなかったマスがある」ときも true にする

- 状態：承認

### 状況（何に迷ったか）

api-spec.md は「新しい順に最大200件。それ以上ある場合は truncated: true」。マスごとに最大200件しか読まないので、範囲内に何件あるかを正確には数えられない。

### 決めたこと

範囲内に200件より多い、**または** どれかのマスで Query が200件で打ち切られた（`LastEvaluatedKey` がある）とき `truncated: true`。

### 理由

読み切れなかったマスに範囲内のピンが残っているかもしれないため。多めに「拡大してください」と出るほうが、黙って欠けるより安全。

### ほかの案

- マスごとに全部読む（ページ送り）：ユニットを使いすぎる

### 影響・あとで見直すこと

ピンが多い場所では、範囲内が200件未満でも `truncated: true` になることがある。api-spec.md に「（かもしれない）」と書き足した。

## 判断：位置のぼかしは「半径×√乱数」で、乱数は crypto を使う

- 状態：承認

### 状況（何に迷ったか）

「半径100mの円の中で、偏らない方法で」ずらすよう指示された。乱数の作り方と、度への直し方は書かれていなかった。

### 決めたこと

- 距離 ＝ 100m × √(乱数)、向き ＝ 360度 × 乱数。√ を付けると円の中で面積あたり同じ確率になる（付けないと中心に集まる）
- 乱数は `Math.random` ではなく Node の `crypto.randomBytes` から作る（予測されにくくするため）
- m を度に直すのは地球を半径6,371kmの球として計算。結果は小数6桁（約0.1m）に丸める
- ずらした後の位置が日本の範囲（20〜46度など）を少し出ても、そのまま保存する
- テストで、2000回すべて100m以内、半径50m以内に入る割合が面積比どおり約25%であることを確かめた

### 理由

- 公式どおりの方法で、短く書ける
- `Math.random` は、条件によっては続きの値を推測される可能性がある

### ほかの案

- 正方形の中でランダムにして円の外は捨てる（棄却法）：同じく偏らないが、ループが要る

### 影響・あとで見直すこと

- 同じ人が同じ場所に何度もピンを立てると、平均で元の位置に近づく（app-spec.md・decisions.md の未決定の「平均化攻撃」）。今回は対策していない

## 判断：市町村の変換表は muni.js から生成し、市町村コードを5桁にそろえる

- 状態：承認

### 状況（何に迷ったか）

「muni.js 相当の変換表をリポジトリに入れる」と指示された。試しに国土地理院APIを呼ぶと、札幌は `"muniCd":"01102"`（先頭0あり）が返ったが、muni.js のキーは `"1102"`（先頭0なし）で、そのままでは引けなかった。

### 決めたこと

- 2026-11-17 に https://maps.gsi.go.jp/js/muni.js を取得し、`infra/scripts/gen-muni-table.mjs` で `infra/lambda/api/muni-table.ts`（1919件）を作った。muni.js 自体はリポジトリに入れていない（作り直すときは同じ手順で取得する）
- キーは5桁にそろえる（`01102`）。APIの値も5桁にそろえて引く。Pins の `cityCode` と Rankings の `key` も5桁
- 名前は「都道府県＋市区町村」で、muni.js の全角空白を取り除く（`北海道札幌市　中央区` → `北海道札幌市中央区`）
- 変換表にないコードが返ったときは「不明」（`cityCode: null`）にする
- ファイルの先頭に出典（国土地理院）を書いた

### 理由

- TypeScript のファイルにすると、Lambda にまとめて入れる（バンドル）ときに追加の設定が要らない
- 生成スクリプトを残せば、市町村の合併などがあっても作り直せる

### ほかの案

- JSON ファイルにする：tsconfig の変更（`resolveJsonModule`）が要る
- Lambda から毎回 muni.js を取りに行く：遅く、失敗の原因が増える

### 影響・あとで見直すこと

- Lambda のファイルが約160KB になった（変換表の分）。動きには問題ない
- 国土地理院のコンテンツ利用規約に沿って出典を書いた。提出物の README などにも出典を書くか、チームで確認する

## 判断：国土地理院APIのタイムアウトは2秒

- 状態：承認

### 状況（何に迷ったか）

「タイムアウトは短めに」と指示された。具体的な秒数は書かれていなかった。

### 決めたこと

2秒（`infra/lambda/api/geocoder.ts` の `GEOCODE_TIMEOUT_MS`）。タイムアウト・HTTPエラー・`{}`・形の違う返事は、すべて「不明」で投稿を成功させる。ログにはエラーの種類だけを出し、URL（位置）は出さない。

### 理由

手元のPCから3回試したときの応答は0.27〜0.70秒だった（東京のLambdaからはこれより速い見込み）。Lambda の制限時間は10秒なので、2秒待っても DynamoDB の書き込みに十分な時間が残る。

### 影響・あとで見直すこと

本番で「不明」が多ければ、ログ（`reverse geocode failed`）を見て時間を延ばす。

## 判断：POST /api/pins の入力チェックの細かい部分をこう解釈した

- 状態：提案（フロント担当の確認待ち）

### 状況（何に迷ったか）

api-spec.md には、スタンプの値の範囲、省略したときの値、メモの数え方、チェックの順番がはっきり書かれていなかった。

### 決めたこと

- `stamp`：`kayui`／`itai` だけ（api-spec.md「5.」で「ピンを立てるとき」のもの）。省略か `null` ならスタンプなしで、返すときは `null`。必須にするかは未決定なので任意にした
- `memo`：前後の空白を除いて、`/api/me` のニックネームと同じ数え方（絵文字も1文字）で100文字まで。改行は使える（`\r\n` は `\n` にそろえる）。タブなどほかの制御文字は 400。省略なら `""`
- `lat`・`lng`：数（JSON の number）だけ。`"35.6"` のような文字列は 400。範囲の端（20・46・122・154）は OK
- 順番：ログイン 401 → 入力 400 → プロフィール 403。入力が正しくないときに Users を読まずに済む
- 本文に `userId` があっても無視する
- POST の返事は api-spec.md の例どおり `commentCount`・`reactions` を含めない
- `GET /api/pins` の範囲は `35.68` のような小数の形だけ（`1e3`・`Infinity`・空は 400）、`min ≤ max`、0.5度ちょうどは OK（小数の誤差のため 0.000000001 の余裕を持たせた）

### 影響・あとで見直すこと

画面の入力チェックも同じにする必要がある。api-spec.md に書き足した。

## 判断：件数（Rankings・pinCount）の更新はトランザクションにせず、失敗しても投稿は成功にする

- 状態：承認

### 状況（何に迷ったか）

ピンを立てると、Pins 1件・Rankings 3件・Users 1件を書く。まとめて書く方法（トランザクション）にするか、途中で失敗したらどうするかは書かれていなかった。

### 決めたこと

- まず Pins に保存し、そのあと件数の更新（Rankings 2〜3件・Users の `pinCount`）を同時に行う
- 件数の更新が失敗しても、201 を返す。失敗した件数と pinId だけをログに出す
- Users の `ADD pinCount 1` は「項目があるときだけ」の条件付き（未登録の人の項目を作らないため）
- Rankings の `label` は、毎回最新のニックネーム・市町村名で上書きする

### 理由

- トランザクションは書き込みユニットを2倍使う。Rankings（5ユニット）に1回で6ユニットかかり、1件の投稿で上限を超える
- ピンが保存できたのに 500 を返すと、利用者がもう一度押して同じピンが2つできる
- DynamoDB の一時的なエラーは、AWS のライブラリが自動でやり直す

### ほかの案

- トランザクション（TransactWriteItems）：数がずれないが、ユニットが足りない
- 件数が失敗したら 500：ピンが重複する

### 影響・あとで見直すこと

まれにランキングの件数が実際のピンの数より少なくなることがある。ハッカソンでは許す。

## 判断：ULID を自作した（ライブラリを入れない）

- 状態：承認

### 状況（何に迷ったか）

api-spec.md の ID は「ULIDを想定」。作り方は書かれていなかった。

### 決めたこと

`infra/lambda/api/ulid.ts` に20行ほどで自作した（時刻48ビット＋乱数80ビット、Crockford の Base32、26文字）。乱数は `crypto.randomBytes`。

### 理由

小さい処理なので、依存を増やさないほうが管理が楽。

### ほかの案

- `ulid` パッケージ：依存が1つ増える
- `crypto.randomUUID()`：作成順に並ばない

### 影響・あとで見直すこと

同じミリ秒の中での並び順は保証しない（Pins の `sk` は日時が先頭なので、地図の並びには影響しない）。
