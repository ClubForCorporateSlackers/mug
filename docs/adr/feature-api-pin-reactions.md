## 判断：スタンプの件数は Pins の `reactions` から読む（強い整合性の GetItem 1回）

- 状態：承認（11/19 小松。decisions.md #37 に移した）

### 状況（何に迷ったか）

PR #16 の #13 は返す形だけを決めていて、件数を Pins の `reactions` から読むか、Reactions テーブルで数えるかは書かれていない。

### 決めたこと

今ある `pins.getReactions()`（Pins を GetItem、強い整合性）で読み、0件の種類は `nonZeroReactions()` で除く。PUT／DELETE（#7・#8）と同じ読み方。

### 理由

押す・取り消すときに、Reactions と Pins の件数はトランザクションでそろえて書いている（docs/adr/feature-api-social.md）ので、Pins の件数は正しい。Reactions で数えると、そのピンの全部の行を Query することになり、押された数に比例して読み込みが増える。強い整合性にしたのは、押した直後に開き直しても古い数が出ないようにするため（1ユニット。結果整合性なら0.5で、差は小さい）。

### ほかの案

- Reactions を Query して数える：読み込みが件数に比例するのでやめた
- 結果整合性で読む（0.5ユニット）：PUT／DELETE と読み方がずれ、直後に古い数が見えることがあるのでやめた

### 影響・あとで見直すこと

ピンを1回開くごとに Pins の読みを1ユニット使う。Pins の読みが足りなくなったら、結果整合性に変えることを考える。

## 判断：自分が押したものは、Reactions を GetItem で3回（種類の数だけ）同時に読む

- 状態：承認（11/19 小松。decisions.md #37 に移した）

### 状況（何に迷ったか）

Scan を使わず、少ない読み込みで「自分が押したもの」を調べる方法を決める必要があった。

### 決めたこと

Reactions の `sk` は `種類#userId` なので、キーは `odaiji#<sub>`・`kaite#<sub>`・`wakaru#<sub>` と最初から分かる。今ある `reactions.has()`（GetItem、結果整合性）を3回同時に呼ぶ（0.5 × 3 = 1.5ユニット）。PUT／DELETE の同じ処理も、この関数（`myReactionTypes`）にまとめた（動きは同じ）。ログインしていないときは Reactions を読まない。プロフィールも確かめない（Users を読まない）。

### 理由

読み込みが、そのピンのスタンプの数に関係なく一定になる。権限の追加もいらない（Reactions の GetItem は許可済み）。

### ほかの案

- BatchGetItem：通信は1回だが読み込みのユニットは同じ。権限の追加と、取りこぼし（UnprocessedKeys）の処理が要るのでやめた
- Query で pinId の行を全部読み、userId で絞る：絞り込みでは読み込みが減らないのでやめた

### 影響・あとで見直すこと

スタンプの種類を増やすと、GetItem の回数も増える。

## 判断：X-Id-Token が「ない」なら `myReactions: []`、「あるが正しくない・期限切れ」なら 401

- 状態：承認（11/19 小松。decisions.md #37 に移した）

### 状況（何に迷ったか）

PR #16 の #13 は「X-Id-Token があれば myReactions に自分が押したものを入れる。なければ []」とだけ書いていて、トークンが正しくないときの扱いがない。

### 決めたこと

`auth.ts` に `optionalUserId()` を足した。ヘッダーがない（空の文字列も含む）なら `undefined` でログインしていない人として扱い、あれば `requireUserId()` と同じように確かめて、正しくなければ 401 `UNAUTHORIZED`。順番は トークン 401 → pinId の形 404 → ピンがない 404。ピンがないとき（形がおかしい pinId、消したピンも）は 404 `NOT_FOUND`（コメント一覧と同じ）。

### 理由

トークンを送ってきたのはログインしているつもりの人なので、黙って `[]` を返すと「押していない」と違う表示になり、ログインが切れていることにも気づけない。ほかの 🔒 の API とも同じ動きになる。画面（PR #16 の `openPin`）はエラーを捕まえて一覧の件数を出し続けるので、401 でも画面は壊れない。

### ほかの案

- 正しくなければ `[]`：違う表示になり、トークンの問題を隠すのでやめた

### 影響・あとで見直すこと

api-spec.md の #13 には、PR #16 が main に入ってから「正しくないトークンは 401」と「ピンがなければ 404」を書き足す。
