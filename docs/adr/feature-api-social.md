## 判断：APIで見せる pinId を「cell-ULID」の形にする（GSIを使わずに Pins を引くため）

- 状態：提案（人の確認待ち）。実装前に案を出し、会話の中で小松さんがこの案を選んだ

### 状況（何に迷ったか）

コメント・スタンプのAPIは URL の `pinId` からピンを見つけて `commentCount`・`reactions` を増やす。しかし Pins のキーは `cell`（geohash）と `sk`（`日時#ULID`）で、ULID だけでは GetItem・UpdateItem ができない。GSI はユニットを使うので使わない（db-schema.md）。本番にはテスト用のピンがすでに2件ある。

### 決めたこと

- APIで見せる `pinId` を **`<cell>-<ULID>`**（例：`xn76-01JDQ3…`）にする（`infra/lambda/api/pin-id.ts`）
- `sk` の日時は ULID の先頭（作成時刻のミリ秒）から計算し直す。`createPin` は同じ時刻から `createdAt` と ULID を作っているので、`nowJst(ULIDの時刻)` は保存した `createdAt` と必ず同じになる
- **DB の中は変えない**。Pins の `pinId` 属性、Comments・Reactions のパーティションキーは ULID のまま
- `GET /api/pins`・`POST /api/pins` は、返すときに `cell` を付ける（地図の Query で `cell` も読むようにした）
- 形が違う `pinId`（`cell-` がない、ULID でない）は「そのピンはない」として 404
- api-spec.md の「共通のルール」に `pinId` の形を書き足し、例を `xn76-01JD…` にした

### 理由

- GetItem・UpdateItem 1回でピンを引ける（読み書きが一番少ない）
- 本番の2件も、地図のAPIが `cell-ULID` の形で返すようになるので、**移し替えなしでそのまま使える**
- DB の形を変えないので、db-schema.md の変更は説明の追記だけで済む

### ほかの案

- Pins に「ULID → cell・sk」の目印の項目を足す：pinId は仕様どおりだが、ピンの投稿で書き込みが1件増え、本番の2件には手で目印を足す必要がある
- GSI（pinId で引く）：ユニットを追加で使う。db-schema.md の「GSIは使わない」と合わない
- `cell` で Query して pinId で絞り込む：1マスのピンを全部読むのでユニットを使いすぎる

### 影響・あとで見直すこと

- **フロントは `pinId` を中身を気にせず、そのまま URL に入れる**こと（ULID だけを取り出して使わない）
- geohash の文字数（`GEOHASH_PRECISION`）を変えると、それより前のピンの `cell` と合わなくなる。変えるときは注意（pinId の形のチェックは1〜12文字を許している）
- `createPin` で `createdAt` と ULID を別々の時刻から作るように変えると、`sk` を計算し直せなくなる（`test/comments-api.test.ts` の「POST /api/pins の pinId から、保存したピンのキーが分かる」で気づける）
- 本番の2件の Pins に `reactions`（空の `{}`）が入っている前提で、スタンプのAPIを作っている（`createPin` は最初から `{}` を入れている）

## 判断：コメントは「Pins の件数を先に増やす → Comments に保存」の順で、トランザクションにしない

- 状態：提案（人の確認待ち）。実装前に案を出し、会話の中で小松さんが「スタンプだけトランザクション」を選んだ

### 状況（何に迷ったか）

コメントすると Comments 1件と Pins の `commentCount` を書く。まとめて書く（トランザクション）か、どちらを先に書くかは書かれていなかった。

### 決めたこと

1. Users を読む（プロフィールがなければ 403）
2. Pins を `ADD commentCount 1`（条件：`attribute_exists(pinId)`）。条件に合わなければ「ピンがない」として 404
3. Comments に PutItem

### 理由

- 先に Pins を条件付きで書けば、ピンがあるかの確認が書き込み1回で済み（読み込みを足さない）、ないピンにコメントが残ることもない
- トランザクションにすると書き込みユニットが2倍になり、Comments（2ユニット）を1件で使い切る

### 読み書きのユニット（db-schema.md の配分との比較）

| 操作 | 書き込み | 読み込み |
|---|---|---|
| コメントする | Pins 1（3のうち）＋Comments 1（2のうち） | Users 0.5（3のうち） |
| コメント一覧 | なし | Pins 0.5（10のうち）＋Comments 0.5〜3.5（3のうち。100件×約250バイト＝約25KBで3.5） |

コメント一覧は、100件たまると Comments の読み込み（3）を少し超えるが、使っていない分（最大300秒分）を先に使えるので、ハッカソンの使い方では問題にならない見込み。

### ほかの案

- トランザクション：件数はずれないが、ユニットが2倍
- Comments を先に保存：ピンがないときに、どこにも表示されないコメントが残る

### 影響・あとで見直すこと

- Pins を増やしたあと Comments の保存に失敗すると 500 を返し、`commentCount` が1多くなる（ハッカソンでは許す）

## 判断：コメントの入力チェックとエラーの順番をこう解釈した

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

api-spec.md は `text` が「1〜100文字」とだけ書いている。数え方、改行、チェックの順番、コメント一覧で存在しないピンを指定したときの扱いは書かれていなかった。

### 決めたこと

- `text`：ピンのメモと同じ数え方（前後の空白を除く、絵文字も1文字、改行は使えて `\r\n` は `\n` にそろえる、タブなどほかの制御文字は 400）。空白だけは 400
- 順番：ログイン 401 → `pinId` の形 404 → 入力 400 → プロフィール 403 → ピンがない 404
- コメント一覧（GET）でも、ピンがなければ 404（Pins を GetItem 1回、0.5ユニット）。空の配列を返すより、フロントが「ピンが消えた」と分かる
- `userId` は返さない。返すのは `commentId`・`nickname`・`text`・`createdAt` だけ（DBからも `userId` を読まない）

### 影響・あとで見直すこと

画面の入力チェックも同じにする。api-spec.md の 5・6 に書き足した。

## 判断：app.ts の振り分けに「パスに値が入るAPI」の仕組みを足した

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

今までの振り分けは「メソッド パス」の完全一致だけで、`/api/pins/{pinId}/comments` のように値が入るパスを扱えなかった。

### 決めたこと

`app.ts` に `paramRoutes`（[メソッド, 正規表現, 処理]）を足した。完全一致を先に探し、なければ正規表現を順に試す。`{pinId}` の値は `decodeURIComponent` してから渡す（壊れた `%` はそのまま渡し、pinId の形のチェックで 404 になる）。

### 理由

ライブラリ（ルーター）を入れるほどの数ではない。今までの書き方（1行足す）に近い形にした。

### ほかの案

- ルーターのライブラリ：依存が増える
- パスを `/` で区切って if 文で分ける：APIが増えると読みにくい

## 判断：スタンプは Reactions と Pins の件数をトランザクションでまとめて書く

- 状態：提案（人の確認待ち）。実装前に案を出し、会話の中で小松さんが「スタンプだけトランザクション」を選んだ

### 状況（何に迷ったか）

「1人1種類1回、二重に押しても件数は増えない」「Pins の reactions も増減」を、どう書けば件数がずれないかは書かれていなかった。decisions.md #26 ではピンの投稿のときにトランザクションを使わないと決めているが、理由は「Rankings のユニットを超える」ためだった。

### 決めたこと

- 押す：TransactWriteItems で「Pins の `reactions.<種類>` を1増やす（条件：ピンがある）」と「Reactions に Put（条件：まだない）」を1つにまとめる
- 取り消す：「Pins の件数を1減らす（条件：ピンがある）」と「Reactions を Delete（条件：ある）」をまとめる
- 条件に合わなかったとき、取り消しの理由（`CancellationReasons`）の並び順で、「ピンがない」→ 404、「もう押している／押していない」→ 何もせず 200、を見分ける。ほかの理由（同時に書き込んだなど）は 500
- 返す `reactions` は、書いた直後の Pins を**強い整合性**で読む（1ユニット）。`myReactions` は、今の種類は結果から分かるので、残り2種類だけ Reactions を GetItem する
- Lambda の権限に `TransactWriteItems` は足していない。トランザクションには専用の権限がなく、中の書き込みごとの権限（Pins の UpdateItem、Reactions の PutItem・DeleteItem）で許可される（**デプロイ後に本物で動くか確かめてほしい**）

### 理由

- 「Reactions は書けたが Pins の件数は増えなかった」が起きると、もう一度押しても（すでにあるので）直らない。トランザクションならどちらも書かれるか、どちらも書かれないかのどちらか
- ピンがないときに Reactions だけ残ることもない

### 読み書きのユニット（db-schema.md の配分との比較）

トランザクションの書き込みは1件（1KBまで）で2ユニット。

| 操作 | 書き込み | 読み込み |
|---|---|---|
| スタンプを押す・取り消す | Pins 2（3のうち）＋Reactions 2（2のうち） | Users 0.5（3のうち）＋Pins 1（10のうち）＋Reactions 1（3のうち。0.5×2件） |

1秒に1回押すと Reactions の書き込み（2）をちょうど使い切る。続けて押されても、使っていない分（最大300秒分）があるので、ハッカソンの人数なら問題にならない見込み。コメント（Pins 1）と同じ1秒に重なると Pins は 3/3。

### ほかの案

- トランザクションなし（Reactions を条件付きで Put してから Pins を増やす）：ユニットは半分だが、途中で失敗すると件数がずれたまま直らない
- Pins の件数を毎回 Reactions から数え直す：地図を開くたびに読み込みが増える

### 影響・あとで見直すこと

- すでに押している人がもう一度押したときも、取り消された書き込みのユニットは使われる
- 取り消して0件になった種類は Pins に `0` が残る（APIでは返さないので見た目は変わらない）

## 判断：スタンプのAPIの細かい部分をこう解釈した

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

api-spec.md の 7・8 には、種類の範囲、チェックの順番、0件の扱い、`myReactions` の並び、押していないものを取り消したときの扱いが書かれていなかった。

### 決めたこと

- `type` は `odaiji`・`kaite`・`wakaru` だけ。ピンを立てるときの `kayui`・`itai`、大文字（`ODAIJI`）は 400
- 順番：ログイン 401 → `pinId` の形 404 → 種類 400 → プロフィール 403 → ピンがない 404。取り消し（DELETE）にもプロフィールを求める（指示どおり）
- もう押しているものを PUT、押していないものを DELETE しても、エラーにせず 200 で今の状態を返す（画面が2回送っても困らないように）
- `reactions` は0件の種類を含めない（api-spec.md の例に合わせた）。`GET /api/pins` の `reactions` も同じにした
- `myReactions` は `odaiji`・`kaite`・`wakaru` の順
- 自分のピンにも押せる（app-spec.md の要相談「自分のピンに押せるか」。止める処理は入れていない）

### 影響・あとで見直すこと

自分のピンに押せないようにするなら、Pins の `userId` を読む処理が要る（読み込みが少し増える）。api-spec.md の 7・8 に書き足した。

## 判断：血液型ランキングに「答えない（UNKNOWN）」を出さない

- 状態：提案（人の確認待ち）。実装前に案を出し、会話の中で小松さんが「表示しない」を選んだ。app-spec.md の要相談（F-08・P4・要相談のまとめ 11）なので、チームの確認が要る

### 状況（何に迷ったか）

app-spec.md で「『不明』として出すか、出さないか」が要相談のまま。件数は feature/api-pins で `key: "UNKNOWN"`・`label: "不明"` として数えている。

### 決めたこと

`GET /api/rankings?type=blood` で `UNKNOWN` を除く（`infra/lambda/api/ranking-api.ts` の `HIDDEN_KEYS`）。除いたあとで順位を付ける。件数は今までどおり数える。

### 理由

血液型ランキングは「どの血液型が刺されやすいか」を見るもの。「不明」が1位になると意味が伝わりにくい。

### 影響・あとで見直すこと

チームで「出す」に決まったら、`HIDDEN_KEYS` から `UNKNOWN` を消すだけで戻せる（件数は残っている）。app-spec.md の2か所に今の扱いを書いた（🟡 のまま）。

## 判断：ランキングは1回の Query（Limit 1000）で読み、Lambda で並べて順位を付ける

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

db-schema.md は「`pk` で Query して、Lambda の中で件数の多い順に並べる」。AGENTS.md は「Query と Limit を使う」。1か月の件数が何件になるか、`Limit` をいくつにするか、同じ件数の並びと順位の付け方は書かれていなかった。

### 決めたこと

- `pk`（例：`2026-11#user`）で Query 1回、`Limit` 1000、続き（ページ送り）は読まない
- 件数の多い順。同じ件数なら `key`（userId・市町村コード・血液型）の順にして、毎回同じ並びにする
- 順位は「同じ件数は同じ順位、次は人数ぶん飛ばす」（1, 2, 2, 4）。上位20件で切る（20件目と同じ件数の21件目は出ない）
- 0件以下の項目は出さない
- `month` は `YYYY-MM`（月は01〜12）だけ。未来・過去の月はそのまま読む（0件なら `items: []`）。省略したら日本時間の今月（UTC の 11/30 15:00 は日本時間で 12/1 なので 12月）
- `userId` は返さない（`label` のニックネームだけ）

### 理由

1件は約100バイトなので、1000件でも約100KB（約13ユニット）。ハッカソンの人数（数十人）なら1回で全部読め、Rankings の読み込み（4）でも1回あたり 0.5〜2 ユニットに収まる。

### 読み書きのユニット

| 操作 | 書き込み | 読み込み |
|---|---|---|
| ランキングを見る | なし | Rankings 0.5〜2（4のうち。100件で約10KB＝1.5） |

### ほかの案

- 全部読むまでページ送り：件数が多いときに読み込みが増え続ける
- 件数の順に並ぶ GSI：ユニットを使う。db-schema.md の「GSIは使わない」と合わない

### 影響・あとで見直すこと

- 1か月に1000人（または1000市町村）より多くなると、読まなかった分は順位に入らない。そのときは「上位だけ別の項目に持つ」などに変える
- 人のランキングの名前は、その月に最後にピンを立てたときのニックネーム（app-spec.md の要相談「変更したときのランキングの表示名」。今は変えていない）
