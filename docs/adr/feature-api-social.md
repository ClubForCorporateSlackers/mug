## 判断：APIで見せる pinId を「cell-ULID」の形にする（GSIを使わずに Pins を引くため）

- 状態：提案（人の確認待ち）。実装前に案を出し、会話の中で小松さんがこの案を選んだ

### 状況（何に迷ったか）

コメント・スタンプのAPIは URL の `pinId` からピンを見つけて `commentCount`・`reactions` を増やす。しかし Pins のキーは `cell`（geohash）と `sk`（`日時#ULID`）で、ULID だけでは GetItem・UpdateItem ができない。GSI はユニットを使うので使わない（db-schema.md）。本番にはテスト用のピンがすでに2件ある。

### 決めたこと

- APIで見せる `pinId` を **`<cell>-<ULID>`**（例：`xn76-01JDQ3…`）にする（`infra/lambda/api/pin-id.ts`）
- `sk` の日時は ULID の先頭（作成時刻のミリ秒）から計算し直す。`createPin` は同じ時刻から `createdAt` と ULID を作っているので、`nowJst(ULIDの時刻)` は保存した `createdAt` と必ず同じになる
- **DB の中は変えない**。Pins の `pinId` 属性、Comments・Reactions のパーティションキーは ULID のまま
- `GET /api/pins`・`POST /api/pins` は、返すときに `cell` を付ける（地図の Query で `cell` も読むようにした）
- 形が違う `pinId`（`cell-` がない、ULID でない）は「そのピンはない」として 404
- api-spec.md の「共通のルール」に `pinId` の形を書き足し、例を `xn76-01JD…` にした

### 理由

- GetItem・UpdateItem 1回でピンを引ける（読み書きが一番少ない）
- 本番の2件も、地図のAPIが `cell-ULID` の形で返すようになるので、**移し替えなしでそのまま使える**
- DB の形を変えないので、db-schema.md の変更は説明の追記だけで済む

### ほかの案

- Pins に「ULID → cell・sk」の目印の項目を足す：pinId は仕様どおりだが、ピンの投稿で書き込みが1件増え、本番の2件には手で目印を足す必要がある
- GSI（pinId で引く）：ユニットを追加で使う。db-schema.md の「GSIは使わない」と合わない
- `cell` で Query して pinId で絞り込む：1マスのピンを全部読むのでユニットを使いすぎる

### 影響・あとで見直すこと

- **フロントは `pinId` を中身を気にせず、そのまま URL に入れる**こと（ULID だけを取り出して使わない）
- geohash の文字数（`GEOHASH_PRECISION`）を変えると、それより前のピンの `cell` と合わなくなる。変えるときは注意（pinId の形のチェックは1〜12文字を許している）
- `createPin` で `createdAt` と ULID を別々の時刻から作るように変えると、`sk` を計算し直せなくなる（`test/comments-api.test.ts` の「POST /api/pins の pinId から、保存したピンのキーが分かる」で気づける）
- 本番の2件の Pins に `reactions`（空の `{}`）が入っている前提で、スタンプのAPIを作っている（`createPin` は最初から `{}` を入れている）

## 判断：コメントは「Pins の件数を先に増やす → Comments に保存」の順で、トランザクションにしない

- 状態：提案（人の確認待ち）。実装前に案を出し、会話の中で小松さんが「スタンプだけトランザクション」を選んだ

### 状況（何に迷ったか）

コメントすると Comments 1件と Pins の `commentCount` を書く。まとめて書く（トランザクション）か、どちらを先に書くかは書かれていなかった。

### 決めたこと

1. Users を読む（プロフィールがなければ 403）
2. Pins を `ADD commentCount 1`（条件：`attribute_exists(pinId)`）。条件に合わなければ「ピンがない」として 404
3. Comments に PutItem

### 理由

- 先に Pins を条件付きで書けば、ピンがあるかの確認が書き込み1回で済み（読み込みを足さない）、ないピンにコメントが残ることもない
- トランザクションにすると書き込みユニットが2倍になり、Comments（2ユニット）を1件で使い切る

### 読み書きのユニット（db-schema.md の配分との比較）

| 操作 | 書き込み | 読み込み |
|---|---|---|
| コメントする | Pins 1（3のうち）＋Comments 1（2のうち） | Users 0.5（3のうち） |
| コメント一覧 | なし | Pins 0.5（10のうち）＋Comments 0.5〜3.5（3のうち。100件×約250バイト＝約25KBで3.5） |

コメント一覧は、100件たまると Comments の読み込み（3）を少し超えるが、使っていない分（最大300秒分）を先に使えるので、ハッカソンの使い方では問題にならない見込み。

### ほかの案

- トランザクション：件数はずれないが、ユニットが2倍
- Comments を先に保存：ピンがないときに、どこにも表示されないコメントが残る

### 影響・あとで見直すこと

- Pins を増やしたあと Comments の保存に失敗すると 500 を返し、`commentCount` が1多くなる（ハッカソンでは許す）

## 判断：コメントの入力チェックとエラーの順番をこう解釈した

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

api-spec.md は `text` が「1〜100文字」とだけ書いている。数え方、改行、チェックの順番、コメント一覧で存在しないピンを指定したときの扱いは書かれていなかった。

### 決めたこと

- `text`：ピンのメモと同じ数え方（前後の空白を除く、絵文字も1文字、改行は使えて `\r\n` は `\n` にそろえる、タブなどほかの制御文字は 400）。空白だけは 400
- 順番：ログイン 401 → `pinId` の形 404 → 入力 400 → プロフィール 403 → ピンがない 404
- コメント一覧（GET）でも、ピンがなければ 404（Pins を GetItem 1回、0.5ユニット）。空の配列を返すより、フロントが「ピンが消えた」と分かる
- `userId` は返さない。返すのは `commentId`・`nickname`・`text`・`createdAt` だけ（DBからも `userId` を読まない）

### 影響・あとで見直すこと

画面の入力チェックも同じにする。api-spec.md の 5・6 に書き足した。

## 判断：app.ts の振り分けに「パスに値が入るAPI」の仕組みを足した

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

今までの振り分けは「メソッド パス」の完全一致だけで、`/api/pins/{pinId}/comments` のように値が入るパスを扱えなかった。

### 決めたこと

`app.ts` に `paramRoutes`（[メソッド, 正規表現, 処理]）を足した。完全一致を先に探し、なければ正規表現を順に試す。`{pinId}` の値は `decodeURIComponent` してから渡す（壊れた `%` はそのまま渡し、pinId の形のチェックで 404 になる）。

### 理由

ライブラリ（ルーター）を入れるほどの数ではない。今までの書き方（1行足す）に近い形にした。

### ほかの案

- ルーターのライブラリ：依存が増える
- パスを `/` で区切って if 文で分ける：APIが増えると読みにくい
