## 判断：PATCH で位置を直せるのは同じ区画（cell）の中だけ。区画の外ならずらし直す（最大20回）

- 状態：承認（11/19 Jiji824。decisions.md #32 に移した）

### 状況（何に迷ったか）

「8.」の #10 は「`lat`・`lng` を送ったら、サーバーがもう一度100mずらしてから保存する」とだけ書いてある。しかし APIで見せる pinId は `<cell>-<ULID>`（decisions.md #27）で、区画（cell）が変わると pinId も Pins のキーも変わる。Comments・Reactions は ULID でつながっているが、画面が持っている pinId は使えなくなる。

### 決めたこと

- ずらした結果の cell が今の cell と違うときは、ずらし直す（最大20回。`geo.ts` の `jitterWithinCell`）
- 20回とも区画の外なら **400 `VALIDATION_ERROR`**（「その位置には動かせません。遠くへ動かすときは、ピンを消して立て直してください」）。何も書かず、地理院APIも呼ばない
- `cell`・`sk`・`createdAt`・pinId は変わらない

### 理由

- 区画の外に出た点を境目に押し戻すと、ピンが境目の線の上にたまって元の位置の手がかりになる。ずらし直すなら、結果は「半径100mの円のうち区画の中の部分」で均等になり、元の点から100m以内という約束も変わらない
- 区画の角（1回で入る確率が約25%）でも、20回なら99.7%入る。乱数の計算だけで、地理院APIは入ったあとに1回だけ呼ぶので負担はない

### ほかの案

- 区画をまたいでもよい（ピンを作り直して pinId を変える）：コメント・スタンプを移す必要があり、画面も pinId の変化に対応が要る。締切に間に合わない
- ずらし直しを5回にする：区画の角では76%しか入らない

### 影響・あとで見直すこと

- 位置を何度も直すと、そのたびに同じ元の点から別の位置が出る。ずっと見ていて平均を取れば、元の点に近づけるかもしれない。これは「位置を直せること」自体の性質で、見えるのは最新の位置だけなので、ハッカソンでは許す
- 区画は約32km×20kmなので、引っかかるのは境目から100m以内のピンだけ

## 判断：DELETE はピンを先に消し、件数はトランザクションにしない。失敗しても 200

- 状態：承認（11/19 Jiji824。decisions.md #33 に移した）

### 状況（何に迷ったか）

指示は「コメント・リアクションを消し、ランキングと pinCount を減らしてから、ピンを消す（scripts/seed/cleanup.ts の手順を参考に）」だった。この順番だと、件数を減らしたあと・ピンを消す前に失敗したとき、利用者がもう一度押すと、件数をもう一度減らしてしまう。

### 決めたこと

1. **Pins を条件付きで消す**（条件：ピンがあり、`userId` がトークンの `sub`）。`ReturnValues: ALL_OLD` で消した中身を受け取る。条件に合わなければ `ReturnValuesOnConditionCheckFailure` で今の中身を見て、あれば 403、なければ 404
2. **ピンを立てた月**（`createdAt` の月）のランキング（人・市町村・血液型）と、Users の `pinCount` を1減らす
3. Comments・Reactions を、そのピンの分だけ消す
4. 200 `{ "pinId": "<cell>-<ULID>" }`

- 件数（2）とコメント・スタンプ（3）は、失敗してもエラーにしない（200 を返し、ログに件数と pinId だけを出す）
- 減らすときは「行があり、1以上のとき」だけ（条件付きの `ADD -1`）。マイナスにしない。0件になった行は消さない（ランキングの表示は0件を出さないので、Rankings に DeleteItem の権限も要らない）
- 3 は Lambda の制限時間（10秒）の前に返事をするため、約6秒でやめる（`deleteBudgetMs`）

この順番は会話でJiji824さんの OK をもらった。

### 理由

- ピンを先に消せば、件数を減らすのは「実際にピンを消せたリクエスト」の1回だけになる。もう一度押されても 404 で、件数は減らない
- ピンを消したあとは、新しいコメント・スタンプは付けられない（どちらもピンがないと 404 になる作り）。残ったコメント・スタンプは、どの画面にも出ない
- トランザクションは書き込みユニットを2倍使い、コメントの数に上限がないので1回（最大100件）に収まらないこともある。ピンを立てるとき（decisions.md #26）と同じく、件数がまれにずれることは許す

### ほかの案

- 子 → 件数 → ピンの順（cleanup.ts と同じ）：上のとおり、もう一度押されると二重に減らす。cleanup.ts は管理者が「もう一度実行して続きを消す」前提で、事情が違う
- 全部をトランザクションにする：ユニットと100件の上限のため選ばなかった

### 影響・あとで見直すこと

- 途中で失敗すると、見えないコメント・スタンプが DB に残る。ハッカソン後の `cdk destroy` で消える
- 「ランキングの件数がずれたときに直す仕組みがない」（Issue #8）は、この API でも同じ

## 判断：コメント・スタンプは BatchWriteItem ではなく DeleteItem で1件ずつ消す

- 状態：承認（11/19 Jiji824。decisions.md #33 に移した）

### 状況（何に迷ったか）

最初の案では BatchWriteItem（25件ずつ）で消すつもりだったが、取りこぼし（UnprocessedItems）のやり直しを考えていなかった。SDK は UnprocessedItems を自動ではやり直さない。

### 決めたこと

- `infra/lambda/api/partition.ts` の `deletePartition`：キー（`pinId`・`sk`）だけを Query（Limit 100）で読み、DeleteItem で1件ずつ消す。ページは `ExclusiveStartKey` で続きから読む
- Comments・Reactions の DynamoDB クライアントは、SDK の自動のやり直しを **5回**（初期値は3回）にする（`DELETE_MAX_ATTEMPTS`）。コメントの投稿やスタンプにも同じ設定が効く

### 理由

- Comments・Reactions の書き込みは2ユニットなので、まとめて送っても1秒に消せる数は同じ
- 1件ずつなら、混んで断られたときは SDK が自動で待ってやり直す。取りこぼしの処理を自分で書かなくてよく、コードが短い。BatchWriteItem の権限も要らない
- 先頭から読み直す方式だと、消した直後のものがまだ見えて（読み込みは少し遅れて反映される）、二重に消すことがあるので、続きから読む

### ほかの案

- BatchWriteItem ＋ UnprocessedItems を待ちながら最大5回送り直す：コードが増えるだけで速さは変わらない

### 影響・あとで見直すこと

- コメントがとても多いピンは、約6秒で打ち切って一部が残る（上の判断のとおり、画面には出ない）

## 判断：立てたときの血液型をピンに保存する（Pins の bloodType）

- 状態：承認（11/19 Jiji824。decisions.md #34 に移した）

### 状況（何に迷ったか）

ピンを消すときに血液型のランキングを減らしたいが、Pins には血液型がない。今のプロフィールの値で減らすと、ピンを立てたあとに血液型を変えた人では、別の血液型の件数が減る。

### 決めたこと

- POST /api/pins で `bloodType`（立てたときのプロフィールの値）を Pins に保存する。APIでは返さない（地図の Query は読む項目を名前で指定していて、`bloodType` は入れていない。テストで確かめた）
- DELETE はこの値で減らす。この項目がない古いピンだけ、Users を読んで今のプロフィールの値を使う
- docs/db-schema.md の Pins の例に `bloodType` を足した。キー・索引は変えない

### 理由

Jiji824さんの提案。キーも索引も変わらず、古いピンの移し替えもいらない。数バイト増えるだけ。

### ほかの案

- 今のプロフィールの値で減らす（ずれを許す）：最初の案。ずれが防げるので変えた

### 影響・あとで見直すこと

- `scripts/seed/cleanup.ts` も今のプロフィールの値で減らしている。このブランチでは直さず、Issue #9 に書き足す（Jiji824さんの指示）

## 判断：403 NOT_OWNER を足し、PATCH・DELETE ではプロフィール登録を確かめない

- 状態：承認（11/19 Jiji824。decisions.md #35 に移した）

### 状況（何に迷ったか）

今のエラーの種類（`infra/lambda/api/http.ts`、api-spec.md の「エラーの形」）に、「自分のものではない」がない。「8.」には `403`（`error: "NOT_OWNER"`）と書いてある。

### 決めたこと

- `ErrorCode` に `NOT_OWNER`（403）を足した。メッセージは「自分が立てたピンだけ変更・削除できます」
- PATCH・DELETE のチェックの順番：ログイン（401）→ `pinId` の形（404）→ 入力（400。PATCH だけ）→ 区画をまたぐ（400。PATCH で位置を送ったときだけ）→ 自分のピンか（403）・あるか（404）
- プロフィール登録（403 `PROFILE_REQUIRED`）は確かめない

### 理由

- 「8.」の案どおり
- 自分のピンかどうか（ピンの `userId` とトークンの `sub`）で十分。Users を読む回数も減る

### ほかの案

- ほかの人のピンも 404 にして、ピンがあることを隠す：地図でだれでも見られるピンなので、隠す意味がない

### 影響・あとで見直すこと

- api-spec.md の「エラーの形」の表に `NOT_OWNER` を足すのは、PR #16 が main に入ってから

## 判断：細かい解釈（PATCH の入力・件数を直す月）

- 状態：承認（11/19 Jiji824）

### 状況（何に迷ったか）

「8.」に書かれていない細かいところ。

### 決めたこと

- PATCH は `stamp`・`memo`・`lat`/`lng` のうち、**本文にある項目だけ**変える。1つもなければ 400。`lat` と `lng` は両方そろっていないと 400。ほかの項目（`city` など）は無視する
- `stamp: null` はスタンプを外す。`memo: null` は `""` にする。チェックのルールは POST と同じ（`pin-api.ts` の部品を共通にした）
- 返す形は POST /api/pins の 201 と同じ（`commentCount`・`reactions` は含めない）で、ステータスは 200
- 市町村ランキングの付け替え（PATCH）と件数を減らす（DELETE）のは、**今月ではなくピンを立てた月**の行。「不明」（`cityCode` が null）の側は何もしない
- PATCH の書き換えは「自分のピンのときだけ」の条件付きで1回。書き換える前の中身（`ALL_OLD`）で古い市町村を知る（先に読んでから書くより読み込みが1回少なく、読んだあとに変わる心配がない）

### 理由

- ランキングは月ごとに「その月に立ったピン」を数えているので、立てた月の分を直さないと合わなくなる

### ほかの案

- 返す形を GET /api/pins の1件（`commentCount`・`reactions` 付き）にする：「8.」に「POST と同じ形」とあるので選ばなかった

### 影響・あとで見直すこと

- api-spec.md に移すとき、上の細かい決まりも「8.」の #10・#11 に書く
