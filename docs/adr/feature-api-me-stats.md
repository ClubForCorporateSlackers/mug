- 期間：2026-11-19 〜

## 判断：`monthCount` は Rankings の今月の「人」の行から読む

- 状態：承認（11/19 Jiji824。decisions.md #38 に移した）

### 状況（何に迷ったか）

PR #16 の案は「今月立てたピンの数」とだけ書いていて、どこから読むかは決まっていない。Rankings の「人」の行と、索引 `byUser` で数える方法の2つがある。

### 決めたこと

Rankings の `pk = <今月>#user`、`key = <sub>` の行の `count` を読む。今月は日本時間で、ピンを立てるときと同じ `nowJst(now).slice(0, 7)` で決める。Lambda に Rankings の GetItem の権限はないので、パーティションキーとソートキーの両方を指定した Query（`Limit 1`、0.5ユニット）で1行だけ読む。行がなければ 0。

### 理由

この行は、ピンを立てると立てた月に +1、消すと立てた月に −1 される（decisions.md #33）。なので「今月に立てて、まだ残っているピンの数」と合う。ランキングの画面と同じ数になり、ピンが増えても読むのは1行（0.5ユニット）で済む。権限の追加もいらない。

ただし、Rankings の Query も結果整合性の読み込み（ConsistentRead なし）なので、索引と同じく、**書いた直後の一瞬は古い値のことがある**（ふつうは1秒以内に反映される）。最初は「すぐに反映される（索引のような遅れがない）」と書いたが、誤りだったので 11/19 に直した。

### ほかの案

- 索引 `byUser` を `sk >= 今月1日` で数える：今月のピンが増えるほど読む量が増え、ランキングの画面とは別の数え方になるのでやめた（書いた直後の一瞬の遅れは、どちらの読み方にもある）
- Rankings の GetItem の権限を足す：Query で同じことができるので、権限は増やさない

### 影響・あとで見直すこと

- ピンを立てたときに Rankings の加算だけが失敗すると、その分だけ少なく出る（ランキングと同じずれ方）
- 書いた直後の一瞬の古い値が困るようになったら、`getCount` を強い整合性（ConsistentRead）で読む（1回 0.5→1ユニット。デプロイし直しが要る）

## 判断：`odaijiReceived` は読むときに数える（索引 byUser で自分のピンを全部読む）。自分で押した分も数え、消したピンの分は数えない

- 状態：承認（11/19 Jiji824。decisions.md #38 に移した）

### 状況（何に迷ったか）

数え方を2つから選ぶ必要があった。A は読むときに数える方法、B はスタンプを押す・取り消すときに Users の数も更新しておく方法。

### 決めたこと

A にした。索引 `byUser` を自分の `userId` で Query し、続きのページがあれば最後まで読む（`GET /api/me/pins` の100件の上限は使わない）。読む項目は `reactions.odaiji` だけにし、合計する（0以下の値は数えない）。

- 自分のピンに自分で押した「お大事に」も数える（Pins の件数には誰が押したかが入っていないため）
- 消したピンの「お大事に」は数えない（消したピンは索引から消えるため。`pinCount` が減るのと同じ考え方）

### 理由

- 既にあるデータ（ダミーのピンの「お大事に」など）を、移し替えなしで正しく数えられる。B で今ある分を入れるには全員分を数える必要があり、Scan が要る
- 毎回数え直すので、数がずれない
- 書き込みのコードを変えずに済む。B だと、押すたびにピンの持ち主を読み（Pins 1）、Users に書く（1）。Users の書きは2ユニットしかない
- ハッカソンの規模なら1人のピンは数十件で、読みは0.5〜1ユニットで済む

### ほかの案

- B（書くときに数える）：既にあるデータの移し替えに Scan が要り、ずれたときに直しにくく、ピンを消すときにも引く処理が要るのでやめた

### 影響・あとで見直すこと

- 読み込みのユニットは、読む項目を絞っても「ピン全体の大きさ」で決まる（合計 4KB ごとに0.5）。1人のピンが100件を超えると、1回で数ユニット使う（索引の読みは2ユニット）
- **重くなったら B に切り替える**。目安は、ピンの多い人の GET /api/me で索引の読み込みの制限（ThrottledRequests）が出たとき。切り替えるときは、今ある分を数えて入れる方法も一緒に決める
- 索引への反映は少し遅れるので、押した直後の一瞬は古い数が出ることがある

## 判断：数の読み込みに失敗したら、2つの項目を付けずに 200 を返す（ログに残す）

- 状態：承認（11/19 Jiji824。decisions.md #38 に移した）

### 状況（何に迷ったか）

GET /api/me は、画面（PR #16）がログインの直後にプロフィールがあるかを確かめるのに使っている。新しく足した読み込み（Rankings・索引）が失敗したときに 500 を返すと、ログインそのものができなくなる。

### 決めたこと

- 順番は今までどおり：ログイン 401 → Users を読み、なければ 404。未登録のときは数を読まない
- 登録済みなら Rankings と索引を同時に読み、どちらかが失敗したら `console.error` にエラーの種類だけを残す（userId やトークンは出さない）。返すものは、`monthCount`・`odaijiReceived` を付けない今までの形で、200
- PUT /api/me の返すものは変えない（追加の読み込みを増やさないため）

### 理由

画面は、項目がなければ「—」を出す作り（`profile?.monthCount !== undefined ? … : '—'`）なので、数が出ないだけで済む。数よりログインのほうが大事。

### ほかの案

- 500 にする：ログインが止まるのでやめた
- 失敗したら 0 を返す：本当の数と区別がつかないのでやめた

### 影響・あとで見直すこと

api-spec.md には、PR #16 が main に入ってから「読み込みに失敗すると、この2つは返らないことがある」と書き足す。
