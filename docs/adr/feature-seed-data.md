## 判断：scripts/seed に独立した package.json を置き、tsx で実行する

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

「Node.js＋TypeScript、infra/ の依存は使わない」と決まっていたが、TypeScript をどう実行するかは決まっていなかった。

### 決めたこと

`scripts/seed/package.json` を新しく作り、AWS SDK v3（Cognito・CloudFormation・DynamoDB・STS）と `tsx` を入れた。ビルドはせず `tsx` で直接実行する。`npm run typecheck`（tsc）で型を確かめられる。サーバーと同じ計算（geohash・pinId の形）は infra/ から import せず、`lib/geo.ts` に写した。

### 理由

ビルドの手順がなくなり、初心者でも `npm run seed` だけで動かせる。infra/ と依存を分けておけば、片方の更新でもう片方が壊れない。

### ほかの案

- tsc でビルドしてから node で実行：手順が増える
- infra/ のコードを import：「infra/ の依存は使わない」に反する

### 影響・あとで見直すこと

サーバーの geohash の文字数や pinId の形を変えたら、`scripts/seed/lib/geo.ts` も直す必要がある。

## 判断：ユーザープールID・クライアントID・テーブル名は CloudFormation から自動で読む

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

スクリプトに渡す設定値の渡し方が決まっていなかった。テーブル名は CDK が自動で付ける名前なので、手で調べるのは手間がかかる。

### 決めたこと

### 理由

値を書き写す手間と、写し間違いをなくすため。どれも秘密ではない。

### ほかの案

- 環境変数や設定ファイルに手で書く：写し間違いが起きやすい

### 影響・あとで見直すこと

スタック名や、テーブルの論理ID（`${id}Table`）を変えたら、`lib/aws.ts` も直す。

## 判断：片付けでは DynamoDB と Cognito を管理者の権限で直接操作する（案1の細かい部分）

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

案1は人が選んだ。ただ、指示の「DBに直接書き込まない」と食い違うように見える。また、ピンの探し方、ランキングの減らし方、途中で止まったときの扱いは決まっていなかった。

### 決めたこと

- 「DBに直接書き込まない」は**投入**についての決まりと解釈した。API にピンを消す機能がなく、Lambda にも Delete の権限がないため、片付けだけは管理者の認証情報で直接消す
- ピンの探し方：(a) 投入のときの記録ファイル（`.seed-state.json`。pinId と投稿者のメールアドレスだけ）と、(b) 設定の場所にかかる cell の Query の両方を使う。**userId がダミーのユーザーのものだけ**を対象にする。Scan は使わない
- ピン1件ごとに「コメント・リアクションを消す → その月の市町村・血液型の件数を1減らす → ピンを消す」の順にする。件数が0以下になったら行を消す（その間に本物の投稿で増えていたら消さない条件付き）。人の行は最後にまとめて消す
- ピンの削除には「userId がダミーのユーザー」の条件を付ける。Cognito のユーザーを消すのも `seed-…@example.com` の形のものだけにする
- 初期設定は確認だけにする。`--execute` を付けたときだけ消す

### 理由

- 記録ファイルだけだと、なくしたときに探せない。cell の Query だけだと、設定を変えたときに見落とす。両方使えば見落としが少ない
- ピン1件ごとに処理すれば、途中で止まってやり直しても、件数を二重に減らすことがない

### ほかの案

- ピンを消す API を追加する（案3）：仕様の変更になり、締切までの作業が増える
- 全部を消してから、件数をまとめて減らす：途中で止まると、件数を直せなくなる

### 影響・あとで見直すこと

- ダミーのピンに本物のユーザーが付けたコメント・スタンプも、一緒に消える（README に書いた）
- ダミーのユーザーが、本物のピンにコメント・スタンプを付けることはない前提（投入スクリプトはダミーのピンにしか付けない）

## 判断：投入にも確認のフラグを付け、二重の投入を止める

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

間違えて実行したときや、2回実行したときの扱いが決まっていなかった。

### 決めたこと

- `npm run seed` だけでは件数を表示するだけ。`--yes` を付けたときだけ入れる
- 前の記録ファイルにピンがあるときは止まる。わざと足すときは `--append` を付ける
- ピンは1件入れるごとに記録ファイルに書く（途中で止まっても片付けられるように）
- 失敗したときのやり直しは、POST は 429 のときだけ（サーバーに届いていないと分かるため。同じピンが2つできるのを防ぐ）、PUT は 5xx でもやり直す

### 理由

本番のDBに入るので、うっかり実行や二重の投入を防ぎたい。

### ほかの案

- フラグなしですぐ実行する：うっかり実行を防げない

### 影響・あとで見直すこと

なし。

## 判断：ダミーのユーザーはメールを送らずに作り、メール確認済みにする

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

`admin-create-user` は、初期設定だと招待メールを送る。宛先の example.com は実在しないドメインなので、送っても届かない。

### 決めたこと

`MessageAction: SUPPRESS`（メールを送らない）と `email_verified=true` を付けて作る。ユーザーがすでにいる場合は作り直さず、新しいランダムなパスワードを設定し直す（`admin-set-user-password`、Permanent）。パスワードは24文字で、大文字・小文字・数字・記号を必ず含める（Cognito の初期設定の条件）。

### 理由

届かないメールを送らないため（送信の失敗が積み重なると、Cognito のメール送信に影響することがある）。パスワードを残さない決まりなので、毎回設定し直す。

### ほかの案

- 一度作ったユーザーを削除して作り直す：sub が変わり、前のデータと結び付かなくなる

### 影響・あとで見直すこと

なし。

## 判断：場所の選び方とばらまく範囲（半径）の決め方

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

具体的な場所と座標、場所ごとに散らす範囲は、決まっていなかった。

### 決めたこと

- 公園は、面積（おおよその値）から同じ広さの円の半径を出し、その**6割**にして、150〜450m の間に収める。円の中では**中心に寄せて**置く（距離＝半径×乱数）。地図を開いたとき、密集して見えるようにするため
- 河川敷は円ではなく、川に沿った線（始点・終点）の左右 `widthM` 以内に置く（多摩川60m、荒川80m、鴨川25m）
- サーバーはさらに最大100mずらすので、6割にしておけば、ほとんどのピンが公園の中かすぐそばに収まる
- 広島は平和記念公園を避けて、中央公園にした（慰霊の場所に「蚊に刺された」を並べるのは不適切なため）
- 座標は私（AI）が覚えているおおよその値。実行前に `npm run places` で地図のリンクを開いて確かめる前提にした
- 投稿者は重み（35・25・20・12・8）で選ぶ。ランキングの「人」に差が出るようにするため

### 理由

公園の大きさに合わせて範囲を変えると、小さい公園からはみ出さず、大きい公園は広く使える。河川敷は細長いので、円で散らすと住宅地に入りやすい。

### ほかの案

- すべての場所を同じ半径にする：小さい公園では住宅地にはみ出す
- 円の中で一様に置く：密集して見えにくい

### 影響・あとで見直すこと

- **座標は地図で確認してから実行する**（とくに河川敷の始点・終点）
- 円の範囲と cell の対応は手元で確かめた（2000点ずつ作り、半径・幅の外と、片付けで探す cell の外に出ないこと）
