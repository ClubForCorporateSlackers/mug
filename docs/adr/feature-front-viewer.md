## 判断：ランキングの3種類は、同時ではなく1つずつ順番に取る

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

最初は `GET /api/rankings` を3種類（user・city・blood）同時に呼んでいた。本番で試すと、3つ目が `Rate Exceeded.` で失敗した。Lambda の同時実行数の上限が **2**（`infra/lib/mug-stack.ts` の `reservedConcurrentExecutions: 2`）のため。

### 決めたこと

`RankingPage` で3種類を順番に（前の結果が返ってから次を）呼ぶ。

### 理由

フロントだけで直せて、APIの仕様を変えずに済む。待ち時間は少し延びるが、ランキングの API は軽いので気にならない。

### ほかの案

- 同時に呼んで、429 のときにやり直す：実装が増える
- 開いているタブの分だけ取る：タブの状態をページに持ち上げる必要があり、変更が大きい

### 影響・あとで見直すこと

**同時実行数2は、デモで何人かが同時に開くと、地図のピンの取得でも `Rate Exceeded` になりうる。** 上限を上げるかはバックエンド（Jiji824）と相談したい。

- → 11/18 Jiji824の指示で、同時実行数を **10** に変えた（docs/decisions.md #31）。何人かが同時に開いたときの負担を減らすため、順番に取る作りはそのまま残した

## 判断：maplibre-gl v6 の Worker ファイルを `?url` でビルドに入れる

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

`npm install maplibre-gl` で入った v6.19.0 は、地図の処理を別ファイル（`maplibre-gl-worker.mjs`）の Web Worker で行う。Vite はこのファイルを自動ではビルドに入れないため、そのままだと Worker の読み込みに失敗し、道路・地名・海の色が出なかった（陰影だけが出る）。

### 決めたこと

`PinMap.tsx` で `import workerUrl from 'maplibre-gl/dist/maplibre-gl-worker.mjs?url'` として同梱し、`setWorkerUrl(workerUrl)` で場所を教える。

### 理由

Worker ファイルは単体で完結している（ほかのファイルを読み込まない）ので、Vite の `?url` でそのまま配信できる。`npm run dev` と `npm run build`（`vite preview`）の両方で、エラーなく表示されることを確かめた。

### ほかの案

- maplibre-gl v5 に下げる：Worker が本体に含まれるので設定は不要だが、古い版を選ぶ理由を別に説明する必要がある
- Worker を CDN から読む：外部への依存が増える

### 影響・あとで見直すこと

ビルド結果に `assets/maplibre-gl-worker-*.mjs`（約550KB）が増える。本体の JS も約1.4MB になり、Vite が「500KBより大きい」と警告を出す（エラーではない）。表示が遅いと感じたら、地図を `import()` で後から読み込むように分ける。

## 判断：表示範囲が0.5度より広いときは API を呼ばず「拡大してください」と出す

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

指示どおり最初は日本全体を表示するが、この範囲は API の上限（縦横0.5度）を超えるので、そのまま呼ぶと 400 になる。

### 決めたこと

- 表示範囲の縦横どちらかが0.5度より大きいときは、API を呼ばずにピンを消し、「ピンを見るには、地図を拡大してください」と出す（app-spec.md F-03 の「広すぎる範囲」）
- 範囲は小数5桁の文字列（`toFixed(5)`）で送る。丸めた後の値で0.5度を判定する
- 地図を動かし終えてから300ミリ秒待って呼ぶ。古い呼び出しの結果は捨てる
- `truncated: true` のときは「ピンが多いので、拡大してください」と出す

### 理由

仕様どおりの範囲チェックを、無駄な呼び出し（Lambda の同時実行数2を使ってしまう）なしで行うため。

### ほかの案

最初から東京駅のあたりを拡大して表示する（app-spec.md の「最初に表示する場所」🟡）。今回は指示が「日本を表示」なので採らなかった。

### 影響・あとで見直すこと

最初の画面ではピンが見えない。デモで不便なら、初期表示を東京などに変える。

- → 11/18 最初の表示を代々木公園あたりに変えた（下の「地図の最初の表示」）。日本全体まで縮小したときの動きは、この判断のまま

## 判断：地図の最初の表示は、現在地（取れなければ代々木公園あたり）にする

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

Jiji824から、最初の表示を app-spec.md の P1 のとおりにするよう指示があった。あわせて、位置情報が使えないときの場所を、仕様の「東京駅」から**代々木公園あたり**に変えるよう指示された（ダミーデータのピンが見えるようにするため）。app-spec.md の F-03 と P1 も、この内容に書き換えた。

指示になかった細かい値は、次のように決めた。

### 決めたこと

- 開いたら、まず代々木公園あたり（経度139.6949、緯度35.6717、ズーム13）を表示し、すぐにピンを取る
- 同時に位置情報を求める（`navigator.geolocation.getCurrentPosition`）。取れたら現在地へ移動する（ズーム14。それより拡大していたらそのまま）
- 位置情報の設定：速さを優先する（`enableHighAccuracy: false`）。1分以内に取った位置は使い回す。10秒で諦める
- 開いたときに許可されない・取れないときは、何も出さずに代々木公園あたりのままにする
- 「現在地」ボタン（新しい基本コンポーネント `LocateButton`）は、右上の拡大・縮小ボタンの下に置く。ボタンで取得している間は、くるくる回るアイコンにして押せないようにする（開いたときの自動の取得では出さない）。失敗したら「位置情報の利用が許可されていません」または「現在地を取得できませんでした」を4秒出す
- 現在地の座標は、地図を動かすのに使うだけ。API に送ったり保存したりしない（送られるのは、これまでどおり表示範囲だけ）
- 現在地を示す印（青い点など）は付けない

### 理由

- 位置情報を待たずに地図とピンを出せば、取得に時間がかかっても、許可を求める表示が出たままでも、画面が空にならない
- ズーム13なら、横幅の広い画面でも表示範囲が0.5度より狭いので、すぐにピンが出る
- 高い精度は不要（ピン自体が100mずらされている）。精度を上げると取得が遅くなりやすい

### ほかの案

- 位置情報が取れるまで地図を出さない：取れないときに長く待たされる
- MapLibre の `GeolocateControl` を使う：現在地の印や追いかける動きまで付いて大げさになる。見た目を shadcn/ui のボタンにそろえられない

### 影響・あとで見直すこと

- 位置情報が取れるのが遅いと、利用者が地図を動かしたあとに現在地へ飛ぶことがある（「取れたら移動する」の指示どおり）。気になるようなら、先に地図を動かした人は飛ばさないようにする
  - → 11/18 Jiji824の指示で直した。**開いたときの自動取得**は、取れるまでの間に利用者が地図を動かしていたら移動しない。**「現在地」ボタン**は必ず移動する。「利用者が動かした」は、MapLibre の `movestart` に `originalEvent`（マウス・指・ホイール・＋−ボタンの操作）が付いているかで見分ける（`flyTo` で動かしたときは付かない）
- 位置情報は、https か localhost でしか使えない（本番とプレビューは https なので問題ない）

## 判断：ピンは MapLibre の HTML マーカーで描き、色は shadcn/ui の色の名前を使う

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

MapLibre のレイヤー（GeoJSON＋circle）で描くと、色の値を直接書く必要があり、frontend/AGENTS.md の「色の値を直接書かない」に反する。

### 決めたこと

ピン1つを `<button>` の HTML マーカーにして、Tailwind のクラスで色を付ける。かゆい＝`bg-destructive`、いたい＝`bg-chart-4`、スタンプなし＝`bg-muted-foreground`。選んだピンは少し大きくして枠を付ける。

### 理由

最大200件なら HTML マーカーでも重くならない。ボタンなのでキーボードでも押せる。

### ほかの案

レイヤーで描き、CSS変数の色を読み取って渡す：shadcn/ui の色は `oklch()` で、MapLibre が読めるかの確認が必要。

### 影響・あとで見直すこと

重なったピンのまとめ表示（クラスター）はしていない（app-spec.md F-03 で 🟡）。

## 判断：画面の作りの細かい決めごと

- 状態：提案（人の確認待ち）

### 状況（何に迷ったか）

指示や仕様書に書かれていない、画面の作りの細かい部分。

### 決めたこと

- **API の型**：`src/lib/api-types.ts` に置き、基本コンポーネントからも型とスタンプの表示名を読み込む（frontend/AGENTS.md の表では、基本コンポーネントが使ってよいものに `@/lib/*` がないが、同じ型を部品ごとに書き直さないため）
- **ピンの詳細**：`GET /api/pins` が返す項目（市町村・スタンプ・メモ・日時・リアクション数・コメント数）だけを出す。コメントの中身（`GET .../comments`）は今回は取らない。リアクションは3種類とも、0件でも「0」と出す。`pinId` は画面に出さない
- **画面の切り替え**：ルーターは入れず、`App.tsx` の状態とヘッダーのボタンで「地図／ランキング」を切り替える。これまでの仮の画面（`HomePage`・`ApiCheckCard`、API の疎通確認）は表示しなくなったが、ファイルは残した
- **shadcn/ui の部品**：`tabs`・`table`・`badge` を追加した
- **地図の CSS**：`maplibre-gl/dist/maplibre-gl.css` を `PinMap.tsx` で読み込む（ライブラリの CSS で、新しい CSS ファイルを作ったわけではない）

### 理由

指示の範囲（見るだけ）で動くことを優先し、変更を小さくするため。

### ほかの案

React Router を入れる：ページが2つだけなので、今は不要。

### 影響・あとで見直すこと

ログイン・投稿の画面を作るときに、ルーターを入れるか、`HomePage` を消すかを決める。
