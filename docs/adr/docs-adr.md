## 判断：これまでの判断を ADR にまとめるときの扱いを決めた

- 状態：承認

### 状況（何に迷ったか）

ADR の仕組みを作るとき、これまでのAIの判断を記録するよう指示された。ただ、次の点は指示に書かれていなかった。

- 過去の判断の期間と、どのブランチの判断として書くか
- まだ `main` に入っていないブランチ（feature/api-me の作業途中のコミット）の判断を含めるか
- 指示にあった判断の一部（feature-api-me.md の `adminUserPassword`）が、gitの履歴に見つからない
- 仕組みの説明を、指示された場所（AGENTS.md・テンプレート・dev-rules.md）以外にも書くか

### 決めたこと

- 期間は、その作業のコミットの日付にした。判断は、そのコミットを最初に含んだ作業ブランチ（`infra/cdk-skeleton`、`worker/cloudflare`、`feature/api-me`）のファイルに入れた
- feature/api-me の作業途中のコミット（c98331c）の判断も含めた。decisions.md #24（プレビューで本番の関数URLを共用）は、そのブランチですでに小松の決定として書かれているので、ADR にはしなかった
- `adminUserPassword` は、指示どおり「承認」で記録し、コードがまだ入っていないことを本文に書いた
- 一般的な ADR との違いの説明は、AGENTS.md の節とテンプレートの冒頭に書いた。`docs/adr/README.md` や README.md の表は、指示にないので作らなかった
- 中身のないコミット（「test: プレビューのビルドを再実行3〜5」）と、人が書いた叩き台（docs/app-spec.md）は、AIの判断ではないので記録しなかった
- この作業は進捗表にないので、進捗表のIDは「なし」にした

### 理由

- コミットの日付とブランチなら、あとで `git show` でたどれる
- 作業途中の判断も、マージの前に人が読めるほうがよい

### ほかの案

- 過去の判断の日付を、記録した日にする：いつ決めたかが分からなくなる
- feature/api-me の判断は、そのブランチで記録する：マージの前に人が読めない

### 影響・あとで見直すこと

- feature/api-me にも docs/adr/feature-api-me.md を足すと、マージのときに同じファイルがぶつかる。docs/adr を先にマージし、feature/api-me はそれを取り込んでから追記するとよい
- feature/api-me をマージしたら、feature-api-me.md の「作業途中のコミット」「コードはまだ入れていない」の説明を直す
