## 判断：Pins に索引（GSI）`byUser`（userId＋sk、全項目、書き3・読み2）を足す

- 状態：提案（人の確認待ち。設計の案は 11/19 にチャットで OK をもらった。decisions.md #36 に書いた）

### 状況（何に迷ったか）

Pins のキーは `cell`（geohash）と `sk` なので、Scan を使わずに「自分のピン」を探す方法がない。db-schema.md には「GSIは使わない」と書いてある（ユニットを節約するため）。

### 決めたこと

- 索引名 `byUser`。パーティションキー `userId`、ソートキー `sk`（`日時#ULID`。今の項目をそのまま使い、新しい順に並べる）
- 入れる項目は **ALL（全部）**
- ユニットは **書き3・読み2**。合計は 書き17・読み25
- **読みの合計が25ちょうどで、余りがない。今後テーブルや索引を足すときは、ほかのユニットを減らして配分し直す**
- Lambda の権限は、この索引の ARN（`<PinsのARN>/index/byUser`）への `dynamodb:Query` だけ。索引名は環境変数 `PINS_USER_INDEX_NAME` で渡す
- `infra/test/mug-stack.test.ts` の「合計25以内」のテストが、テーブルのユニットしか足していなかったので、索引のユニットも足すようにした
- db-schema.md の「GSIは使わない」を書き換え、表・「自分のピンを取るとき」・「4. 操作ごとの読み書き」に索引を足した

### 理由

- 索引なら、ピンを書き込むコード（立てる・直す・消す・コメント・スタンプ）を変えずに済む。既にあるピン（ダミーの約150件など）も、DynamoDB が自動で索引に入れる（バックフィル）
- 索引に入れる項目はあとから変えられない（索引を消して作り直すことになり、デプロイ2回とバックフィルがもう1回いる）。ALL と、返す項目だけ（INCLUDE）の差は `cityCode`・`bloodType` の数十バイトだけなので、ALL にした。索引に `userId` が入っていても、API では返さない（読む項目は `GET /api/pins` と同じ）
- 索引の書きユニットが足りないと、Pins 本体への書き込みまで止められる。そのため Pins と同じ3にした
- 読みは、1回で最大約5ユニット（100件 × 約0.4KB ≒ 40KB、結果整合性で4KBごとに0.5）。画面を開いたときに1回呼ぶだけなので、使わなかった分をためておける（バーストキャパシティ）ことを考えると2で足りる

### ほかの案

- 索引の項目を一部（INCLUDE）にする：ユニットはほとんど変わらず、あとで項目を足すときに索引の作り直しになる
- Users に自分のピンの一覧を持たせる・自分のピン用のテーブルを足す：ピンを立てる・消すたびに書き込みが増え、ずれたときの直し方も要る
- Pins の読みを 10→9 にして、索引の読みを3にする：今のままで足りる見込みなので、地図の読み込みを減らさなかった（人の判断：25ちょうどのままで OK）

### 影響・あとで見直すこと

- **デプロイのとき**（小松さん）：
  - `npx cdk diff` で、Pins テーブルが**作り直し（replace）ではなく更新（update）**になっていることを必ず確かめる（Pins は removalPolicy が DESTROY なので、作り直しだとデータが消える）
  - 索引を作るあいだ（見込み5〜15分）、`cdk deploy` が長くなる。Pins はふつうに読み書きできるが、まれに投稿が遅くなることがあるので、デモの最中は避ける
  - Lambda は Pins テーブルの名前を使うので、CloudFormation は「索引ができる → Lambda の更新」の順に進める
  - `describe-table` の `ItemCount` は約6時間ごとにしか更新されないので、件数の確認には使わない
- 索引への反映は少し遅れることがある（結果整合性）。立てた直後の一瞬は、一覧に出ないことがある
- `scripts/seed/cleanup.ts` もこの索引を使えば短くできるが、今回は直していない
- docs/architecture.md の「ランキング用のGSI」という古い書き方は、今回は直していない
